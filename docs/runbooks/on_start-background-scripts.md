# Фоновый запуск скриптов при загрузке (on_start)

Как корректно выполнять boot-time скрипты **в фоне**, чтобы медленная задача
(например, установщик IDMVS) не блокировала загрузку и не задерживала следующие
скрипты.

## Контекст

Раннер `config.sh::exec_files_in_folder()` выполняет скрипты фазы
(`on_start/{before_login,network_pre,oneshot,forking}/`) **последовательно**,
дожидаясь каждого (`timeout 300 "$script"`). Фаза `oneshot` вдобавок объявлена
`Before=display-manager.service`, поэтому долгий скрипт задерживает выход в UI.

## Почему нельзя просто `installer &`

Юниты `on_start` — `Type=oneshot`. Когда `ExecStart` завершается, systemd
останавливает юнит и по дефолтному `KillMode=control-group` шлёт `SIGTERM`
**всем оставшимся процессам в cgroup**. Скрипт, запущенный через `… &` из тела
on_start, сидит в том же cgroup → его прибьют, как только раннер дойдёт до конца.
`nohup`/`disown` не спасают (это про SIGHUP/job-control, а не про cgroup).
**Фоновая задача обязана жить в отдельном юните/cgroup** — через `systemd-run`
или как самостоятельный сервис.

## ⚠️ Подвох с гонкой (важно для IDMVS)

Если увести установку в фон, вернётся гонка: приложение автостартует при логине,
а IDMVS может быть ещё не доустановлен → падение / «камера не найдена». Именно
поэтому инсталляторы сейчас в `oneshot` с `Before=display-manager` (UI ждёт
установку). **Фон допустим только если приложение не стартует до готовности** —
нужен readiness-гейт (маркер + ожидание в автостарте).

---

## Вариант A — точечный фон через `systemd-run` + readiness-маркер

Конкретную задачу (IDMVS/hasplm) запускаем из on_start-скрипта как отдельный
transient-юнит; приложение ждёт маркер готовности.

**1. Запуск в фоне** (в `on_start/oneshot/001-idmvs.sh` или отдельном скрипте):

```bash
systemd-run --unit=idmvs-install --collect \
  --description="IDMVS SDK install" \
  -p After=network-online.target \
  -p TimeoutStartSec=600 \
  /bin/sh -c '/home/inauto/distr/install_idmvs.sh && touch /run/idmvs-ready'
```

- `install_idmvs.sh` крутится в отдельном `idmvs-install.service`, детачед от
  раннера; on_start-скрипт возвращается сразу, загрузка не блокируется;
- по успешному завершению пишется маркер `/run/idmvs-ready`;
- лог: `journalctl -u idmvs-install`; `--collect` убирает юнит после завершения.

**2. Ожидание в автостарте приложения** (`on_login/` или `.desktop`-launcher):

```bash
# ждём готовности IDMVS до старта приложения (макс. ~120 c)
for _ in $(seq 1 60); do
    [ -e /run/idmvs-ready ] && break
    sleep 2
done
```

Если приложение оформлено как systemd-сервис, вместо ожидания-в-скрипте лучше
выразить зависимость: `After=idmvs-install.service`, `Requires=…`.

**Плюсы:** быстрый boot-to-UI; управляемо и логируемо.
**Минусы:** нужно не забыть про маркер и ожидание, иначе гонка.

## Вариант B — фаза `forking` реально детачит скрипты

Папка `on_start/forking/` + `OnStartForking.service` (`Type=forking`) задумана
под фон, но текущий раннер выполняет её скрипты **последовательно, дожидаясь**
каждого — то есть НЕ бэкграундит. Чинится тем, что для фазы `forking` раннер
запускает каждый скрипт через `systemd-run` (детачед), а не синхронно.

Идея правки `exec_files_in_folder()` (отдельная ветка для forking):

```bash
# для фазы forking — не ждём завершения, запускаем каждый скрипт в своём юните
while IFS= read -r script; do
    unit="onstart-$(systemd-escape "$(basename "$script")")"
    systemd-run --unit="$unit" --collect --description="on_start/forking: $script" \
        "$script"
done < <(find "$TARGET_DIR" -maxdepth 1 -type f -name '*.sh' -executable | sort)
```

Тогда всё, что положено в `on_start/forking/`, стартует конкурентно и не
блокирует ни раннер, ни загрузку. Классический forking-скрипт при этом просто
запускает свой долгоживущий процесс.

**Плюсы:** единый механизм — «положил в forking → выполнится в фоне».
**Минусы:** правка общего раннера; readiness-гейт для зависимых потребителей
(приложение) всё равно нужен, если они не должны стартовать раньше.

## Что выбрать

| Нужно | Решение |
|---|---|
| Гарантия «установлено до UI», простота | оставить как есть: `oneshot` + `Before=display-manager` (ценой долгого boot-to-UI) |
| Быстрый boot-to-UI, одна-две фоновые задачи | **Вариант A** (`systemd-run` + `/run/*-ready` + ожидание в автостарте) |
| Много фоновых задач, единый паттерн | **Вариант B** (детач фазы `forking` через `systemd-run`) |

Для фиксированной задачи вместо запуска через раннер можно вынести установку в
**самостоятельный systemd-сервис** (`config.sh` печёт юнит в образ) —
`Type=oneshot`, `WantedBy=multi-user.target`, без ordering-зависимости он
выполняется параллельно и не блокирует; ретраи/таймауты/логи из коробки.
